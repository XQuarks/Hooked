# 07 · 2D 重制说明（渲染层整体替换）

> **概述**：把渲染层从 three.js 实时 3D 整体换成 Canvas 2D 矢量绘制。玩法层（`src/game/`）一行未改——物理、经济、剧情、存档、UI 全部沿用。产物从 958 KB 降到 370 KB，three.js 完全剔除。
> **状态**：可运行，四套 headless 回归通过，控制台错误 0。
> **读者**：想判断「这版为什么更好 / 还差什么」的人；想继续调画面的人。
> **关联**：`04-重制方案与关键取舍.md`（3D 版选型）、`06-画面升级说明.md`（3D 版画面记录）、`rebuild/README.md`（目录与调参索引）。

## 一、为什么放弃 3D

先把话说清楚：3D 版不是没做完，是**这条路在这个题材上性价比不成立**。

复盘下来有三个死结：

1. **雾把层次压平了。** 水下场景必须有雾才有纵深，但雾一浓，远处的珊瑚、岩壁、鱼全变成同一片青灰。3D 的「真实」在这里反而成了负担——你付出了几何和光照的成本，看到的却是一块渐变色。
2. **程序化几何做不出「精细」。** 没有美术资源，鱼和船只能用基础几何拼。几何一细分，性能掉；不细分，就是「球加三角片」。这条线我在上一版推到了极限（参数化放样、7 头身人物），结果仍然是「像模型，不像画」。
3. **单文件离线绑死了素材方案。** glTF / 贴图会破坏「双击即玩、零请求」，所以只能全程程序化——这恰好是最难做出美术感的路径。

而竖屏手机的实际像素是 430×900。在这个尺寸上，**轮廓、明暗、色彩层次**对观感的影响，远大于多边形数量。

所以结论是：**用 2D 换掉 3D，把预算从「几何精度」挪到「分层与光」。**

### 必须保住的东西

换渲染层不动玩法，这是这次改造的硬约束：

- 世界坐标仍是米制（1 单位 = 1 米），`y` 向上为正，水下为负
- `XW = 3.45` 的横向物理边界、下潜/收线速度、碰撞半径全部不变
- 点击仍是「屏幕 → 世界平面」投影，射击判定不变
- 四个阶段的时序、连击、过热、结算公式不变

实现方式：写一个**与 3D `Stage` 同签名**的 `Stage2D`，engine 只改 import 和几处 three 专有对象。

## 二、坐标与相机

2D 里最容易做错的是坐标符号。规则只有一条：

```
世界 y 向上为正（水面 y=0，水下 y<0），屏幕 y 向下为正
sx = W/2 + wx × scale
sy = H/2 − (wy − cy) × scale
```

- `scale = W / VIEW_W`（`VIEW_W = 7.2` 米），所以**横向可见 7.2 米**，纵向由屏幕比例决定（430×900 时约 15 米）。
- `cy` 是屏幕中心对应的世界 y，由 `setCamera(focusY)` 给出：`cy = focusY + 1.5 + above×0.9`，沿用了 3D 的机位习惯，所以钓钩在画面里的位置感和原来一致。

> 这一步踩过坑：最初写成了 `sy = H/2 + (wy − cy) × scale`，整幅画面上下颠倒。因为背景不依赖世界 y，只有鱼和水面位置反了，一开始被误判成「鱼群生成有问题」。

## 三、画面怎么搭

`Stage2D.render()` 的合成顺序，顺序本身就是画面的成败：

```
背景（天空/水体 → 光柱 → 远/中景剪影 → 远景鱼影 → 焦散光斑 → 统一光照）
  → 船 → 漂流瓶 → 鱼（按 z 从远到近）
  → 鱼钩 → 钓线 → 粒子
  → 近景剪影（压在鱼上面）
  → 入水过渡 / 暗角
```

各层的职责：

| 层 | 做法 | 为什么 |
| --- | --- | --- |
| 水体 | 屏幕内固定「上亮下暗」的四段渐变，再乘深度衰减系数 | 3D 的雾是「整体压平」，这里改成「方向性衰减」，浅水亮、深渊沉，一眼能读出深度 |
| 光柱 | 4 根从屏幕顶端斜射的光锥，外层宽淡 + 内层亮芯，随时间和深度摆动 | 始终从顶端画起并向下渐隐，避免水面在屏幕外时出现水平切边 |
| 焦散 | 16 个柔和椭圆光斑缓慢漂移，加色叠加 | 早期用细线画，看起来像「刮痕」；改成光斑才像阳光被水面聚焦 |
| 剪影 | 远/中/近三层，暗度 −0.20 / −0.52 / −0.90，视差 0.34 / 0.62 / 1.15 | **空气透视**：远的融进雾里，近的压成黑。这一条是拉开纵深的关键 |
| 近景 | 压在鱼之上 | 玩家才会有「从海草后面看过去」的感觉，而不是看一张贴纸 |
| 统一光照 | 顶部 +14% 冷白、底部 −40% 深色 | 把零散元素的明暗拉回同一套光里，避免各画各的 |
| 鱼 | 贝塞尔体形 + 背暗腹亮渐变 + 侧线 + 暗描边 + 逆光背线 | 暗描边保证任何背景下轮廓都在；侧线是最省事的「鳞片反光」暗示 |
| 后期 | 入水水色过渡、落水白闪、径向暗角、噪点颗粒 | 颗粒专治大面积渐变的「塑料感」 |

### 为什么鱼要额外放大

真实比例下，0.34 米的沙丁鱼在 430px 宽屏上只有约 20px——看不见鱼形。所以加了一个随体长递减的视觉放大：

```
grow = max(1.30, 2.00 − len × 0.14)
```

小鱼 ×1.95，鲨鱼 ×1.55。**只改绘制，不改碰撞**，所以手感不受影响。

## 四、去掉的东西

| 移除 | 原因 |
| --- | --- |
| three.js 全量（约 600 KB 源码） | 不再需要 |
| WebGLRenderer ×N（图鉴每条鱼一个） | 换成离屏 2D canvas，图鉴不再抢 GPU 上下文 |
| `EffectComposer` / `Bloom` / `ShaderPass` | 2D 用径向渐变做局部辉光，成本几乎为零 |
| 半分辨率折射 RT | 水面改成多层渐变 + 高光碎片，视觉效果接近但不多一遍渲染 |
| 阴影贴图、PCF | 剪影本身就是影子 |

## 五、体积与性能

| 指标 | 3D 版 | 2D 版 |
| --- | --- | --- |
| 单文件 | 958 KB（gzip 269 KB） | **370 KB（gzip 121 KB）** |
| 构建模块数 | 数百（含 three 全部子模块） | 49 |
| draw call 概念 | 100~180 | 不适用（Canvas 2D 按绘制指令） |
| 每帧渐变对象 | — | 约 30~40 个（光斑/光柱/暗角），高画质 |
| 额外 pass | 折射 + Bloom + 分级 | 0 |
| GPU 依赖 | 必须有 WebGL | 无（软件渲染也能跑） |

2D 的主要开销是**每帧创建的渐变对象**和**大面积填充**，不是三角形。所以画质分级做成「开关装饰层」：

- `low`：DPR 1，关焦散、远景鱼影、颗粒
- `mid`：DPR ≤1.5，关焦散
- `high`：DPR ≤2，全开

## 七、已知不足

诚实列一下，这些是这一版没解决的：

1. **造型精度有限。** 全程程序化矢量，鱼和人物是「能辨识、够干净」，但达不到手绘美术的细腻度。真要再上一档，需要引入位图素材（背景/鱼贴图），代价是单文件体积和一致性风险。
2. **画面偏「扁平」。** 这是矢量风的选择，不是 bug。喜欢厚涂/像素风的玩家可能仍不买账。
3. **动画偏简单。** 鱼只有摆尾 + 轻微浮动，没有转向时的身体弯曲。
4. **冰海辨识度仍靠颜色。** 极光带做得克制，深水区和其他深度带的差异主要靠色调。
5. **移动端真机未实测。** 高 DPR + 大面积渐变在低端机上的帧率没有数据。
