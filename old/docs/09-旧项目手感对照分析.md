## 一、先统一尺子：两个项目怎么比

两个项目用的单位完全不同，直接比数字没有意义。**唯一可比的尺子是「屏幕高/秒」**——
它决定玩家在屏幕上看到东西移动多快，也就是"来不来得及反应"。

| | 旧项目 | 当前 rebuild |
| --- | --- | --- |
| 一屏等于多少世界单位 | `WORLD.viewHeight = 240`，但竖屏会触发 `minViewWidth = 154` → 实际 `vh = 154 / (430/900)` = **322 单位** | 屏幕 900px ÷ 59.7 px/米 = **15.07 米** |
| 尺子 | 1 屏 = 322 单位（竖屏手机） | 1 屏 = 15.07 米 |
| 换算 | ÷ 322 | ÷ 15.07 |

> `VIEW_W = 7.2` 米对应 430px 宽 → 59.7 px/米；竖屏 430×900 → 可见高度 15.07 米。
> 旧项目 `resize()` 里：`vw = vh × aspect`，若小于 `minViewWidth(154)` 就反过来用
> `vh = 154 / aspect` —— 430×900 的宽高比 0.478 会算出 114.7，**一定触发**，所以竖屏是 322 而不是 240。
> （`world.js:2049`）
> 下面所有"屏/s"都按这个算。横向活动区也顺带比一下：旧项目 `playHalfWidth = 56` → 活动区占 73% 屏宽；
> rebuild `XW = 3.45` → 占 96%。**新版左右可躲的空间更大**。

## 二、钩子运动速率

### 2.1 三个速度

| 阶段 | 旧项目 | 当前 rebuild（按 60m 深算） | 差异 |
| --- | --- | --- | --- |
| 下潜 | 100 单位/s = **0.31 屏/s**（穿一屏 3.2s） | `9 + d×0.022` = 10.3 m/s = **0.68 屏/s**（1.47s） | 新版**快 2.2 倍** |
| 收线 | 240 单位/s = **0.75 屏/s**（1.34s） | `13 + d×0.028` = 14.7 m/s = **0.97 屏/s** | 新版快 29% |
| 满钩收线 | —（旧版没有这个加速） | 26 m/s = **1.73 屏/s** | 新版独有 |

再往深看，rebuild 的速度还会随深度线性涨：

| 深度 | 下潜（屏/s） | 收线（屏/s） |
| --- | --- | --- |
| 0 m | 0.60 | 0.86 |
| 60 m | 0.68 | 0.97 |
| 120 m | 0.77 | 1.10 |
| 400 m | **1.18** | 1.61 |

旧项目的注释里专门讨论过这件事：

> 「取 Lv0 的 64 会让中后期每一竿凭空多等 8~12 秒；取 Lv20 的 240 又会让开局的下潜
> 快到来不及躲鱼（240 穿过一屏只要 1 秒）。100 是"还躲得动、也不拖沓"的那一档。」
> —— `config.js:2775`

**结论**：旧项目把"0.31 屏/s"当作躲鱼的下限（每屏 3.2 秒反应时间）。
rebuild 在 400 米时是 1.18 屏/s（0.85 秒一屏），**躲鱼已经从"操作"退化成"运气"**。
`+ d×0.022` 这个随深度加速的系数值得重新审视——旧项目是**恒定速度**，理由是
"速度不该变成玩家看不见的隐形税"。

### 2.2 「下潜 → 刹停 → 收线」这一 Reverse

这是两个项目差距最大的一段，也是我上一轮改了但还是不够的地方。

**旧项目是四段式**（`game.js:873` `_reel()` / `:1059` `_updateAscend()`）：

| 段 | 曲线 | 关键点 |
| --- | --- | --- |
| ① 刹停（reelPre） | `y = y0 − D·(2u − u²)`，D = 60 单位（**0.19 屏**） | **起手速度 = 2D/T = 当时的下潜速度**，末端速度 0 —— 带着惯性滑出去再停 |
| ② 停顿 | `reelPreDur` 兜底 0.8s（只有触底 v0=0 时才用） | |
| ③ 起拉（ascendRamp） | `y = y0 + D·(3u³ − 2u²)`，D = 收线速度×T/5，T = 0.75s | 起手速度 0；**u≈0.44 处先往下沉 13%·D**（anticipation）；末端速度 = 5D/T = 满速 |
| ④ 满速收线 | `y += spd·dt` | |

**当前 rebuild 是两段式**：

| 段 | 做法 | 问题 |
| --- | --- | --- |
| turn | 0.5 秒**完全静止**（`lure.vy = 0`，位置不动） | 没有惯性，像撞墙 |
| ascent | `vy = -4` 起步，加速度 16，直接冲到满速 | 没有 anticipation，也没有"从 0 开始" |

换算一下旧项目的刹停：`D=60 单位 = 0.19 屏`，`v0=100` → `dur = 2D/v0 = 1.2 秒`。
也就是**钩子带着速度又往下冲了近五分之一屏，花 1.2 秒才停住**，然后才往上拉。

rebuild 的 0.5 秒静止对比之下就是"急刹 + 原地发呆"。

### 2.3 镜头跟随率（这条最影响观感）

两个项目都用指数平滑 `pos += (target − pos) × k·dt`。这种平滑有个**数学上的必然滞后**：

```
稳态误差 = 速度 v ÷ 平滑率 k
```

| | 旧项目 | rebuild | 换算成屏高 |
| --- | --- | --- | --- |
| 下潜 | k = 7 → 100/7 = 14.3 单位 | k = 5.5 → 10.3/5.5 = 1.88 m | 旧 4.4% / 新 **12.5%** |
| 收线 | k = 12 → 240/12 = 20 单位 | k = 5.5 → 14.7/5.5 = 2.67 m | 旧 6.2% / 新 **17.7%** |
| 收线（400m） | — | 24.2/5.5 = 4.4 m | 新 **29%** |

旧项目还额外做了一件事：**lead 补偿**。

```js
// game.js:1752
// 相机的 y 是指数平滑跟过去的：dcamY/dt = rate·(ty − camY)。
// 目标匀速 v 时的稳态误差是 camY = ty − v/rate —— 镜头永远落在鱼后面 v/rate。
// 把瞄准点提前 v/rate，稳态误差正好抵消。
const aimY = ty + tvy / rate;
```

**rebuild 没有任何 lead 补偿。** 结果就是：400 米收线时，钩子实际位置比画面中心低 29% 屏高，
叠上 `camOffset` 给的 30% 定位，钩子已经贴到屏幕底边——玩家看不到上方来鱼，
出水时镜头还要猛追一次。这就是"收线上的衔接不流畅"的真正来源。

### 2.4 构图（钩子放在屏幕哪个高度）

| | 旧项目 | rebuild | 差 |
| --- | --- | --- | --- |
| 下潜 | 钩子在中心**上方 30%** 屏高（屏幕 y=20%） | `camOffset` 深处 3.4m → 上方 1.9m = **12.6%** | 少看 **17%** 的下方 |
| 上升 | 钩子在中心**下方 33%** 屏高（屏幕 y=83%） | `lure.y + 3.1` → 下方 4.6m = **30.5%** | 基本一致 ✓ |

叠加 2.3 的滞后，实际观感：

| | 钩子实际屏幕位置（60m） |
| --- | --- |
| 旧项目下潜 | 20% + 4.4% ≈ **24%** |
| rebuild 下潜 | 37.4% + 12.4% ≈ **50%**（正中） |
| 旧项目收线 | 83% + 0（有 lead 补偿） = **83%** |
| rebuild 收线 | 80.5% + 17.7% ≈ **98%**（贴底） |

**下潜时钩子卡在正中间，玩家只能看到下方一半的鱼**；收线时钩子贴底，
上方完全没有预视。这两条合起来，就是"躲鱼/撞鱼全靠反应"的体感来源。

## 三、鱼在天空中的效果

### 3.1 滞空时长：1.5 秒 vs 9 秒——这是设计哲学的分水岭

| | 旧项目 | rebuild |
| --- | --- | --- |
| 初速公式 | `v0 = 240 + √value × 14`（**身价决定弹道**） | `v = max(17, min(25, 收线速度×0.92+3))`（**收线速度决定**） |
| 重力 | 60 单位/s² | 24 m/s² |
| 滞空 | `2v0/g` = **9.1 秒**（沙丁鱼 v0=274）~ **20 秒**（鱼王 v0=605） | `2v/g` = **1.4~2.1 秒** |
| 最高点 | 626~3050 单位 = **1.9~9.5 屏**（飞进太空） | 8~13 米 = **0.53~0.86 屏** |
| 空中阶段时长 | 26 秒硬顶（还随「耐压舱」升级） | 鱼落地就结束，通常 2~4 秒 |

旧项目在 `config.js:2870` 的注释里算得很清楚：

```
√6   → v0 274 → 626m   (沙丁鱼)
√100 → v0 380 → 1204m  (剑鱼)
√680 → v0 604 → 3040m  (黄金鱼王 · 深空)
```

**这就是 Ridiculous Fishing 的精髓**：鱼被甩到天上，你能打很久，打得越久赚得越多。
rebuild 现在的空中阶段只有 1.5 秒，只够开 2~4 枪（手枪 cd 0.30），本质是"过场动画"。

⚠ 但这条**不能单独照抄**：rebuild 的空中镜头上限是 `clamp(top - 2.6, 0.4, 9)`——
镜头最高只到 9 米。鱼要是飞到 75 米（5 屏），早就出画面了。
要延长滞空必须同时放开镜头上限、重新设计空中相机，属于**大改**。

### 3.2 弹道分布：扇形 vs 一堆随机

| | 旧项目 | rebuild |
| --- | --- | --- |
| 水平初速 | `spread = i/(n−1) − 0.5`，再按"目标漂移距离 ÷ 滞空时间"反推 | `lure.x + rand(-0.6, 0.6)` 纯随机 |
| 结果 | 鱼按捕获顺序**扇形铺开**，条数越多扇面越宽 | 全挤在钩子左右 1.2 米内 |
| 画面 | 像撒网 | 像一团 |

旧项目的"先定该飘多远，再反推水平速度"（`game.js:1366`）很值得抄：

```js
const drift = 180 + √value × 24;
const vx = (spread * 2 * drift) / flight;   // 滞空久的鱼不会飘出画面
```

### 3.3 翻滚

| | 旧项目 | rebuild |
| --- | --- | --- |
| 轴 | **三轴**：Z（画面内打滚，主轴 ±7~16 rad/s）+ X ±3.5 + Y ±4.5 | 只有 Z 轴，`rand(-4, 4)` |
| 中弹追加 | **沿当前方向**叠加 `+5~14` | `rand(-7, 7)` 随机方向 |
| 观感 | 翻滚；越打转得越凶 | 转速慢且会突然反向 |

旧项目注释直接点名了这个坑（`fish.js:889`）：

> 「转速沿当前方向叠加而不是重新随机 —— 否则每一枪都像被按了"反向键"，观感是抽搐而不是被炸飞。」

### 3.4 空中相机

| | 旧项目 | rebuild |
| --- | --- | --- |
| 锁定目标 | **最低的那条**非扣钱鱼（最快落水的 = 最该先打） | **最高的**那条 |
| 理由 | "它被击落/落水后自动换下一条，天然形成逐个点杀的节奏"；试过"质心"，画面里经常一条鱼都没有 | — |
| 缩放 | `scale = 0.70`（**推近 30%**） | 无缩放能力 |
| 平滑率 | `rate = 9` | `k = 3.4` |
| lead | `aimY = ty + vy/rate` | 无 |
| 清空后 | **画面定格**在清空那一刻的瞄准点（`_airHold`） | 无 |

旧项目的 `_airCamera()` 注释里有一段实测记录很关键：

> 「v0.3.2 试过"瞄鱼群质心"，**必须回退**：鱼群在空中能拉开 5 个可见高度，
> 质心经常落在"两条鱼之间"的空白处 —— 画面里一条鱼都看不到（玩家实机反馈）。」

rebuild 现在跟"最高的鱼"，其实也有同样的风险：最高那条在屏幕顶上飞，
镜头为了框住它一路抬高，下面那几条已经出画面了。

### 3.5 结算节奏

| | 旧项目 | rebuild |
| --- | --- | --- |
| 清空后等待 | `airSettleGrace = 1.8s`，且**从"清空那一刻"开始计时** | `endT = 1.6s`，同样从 `active === 0` 开始 ✓ |
| 硬顶 | `airTimeout`（26s 起，可升级） | 无 |
| 清空瞬间 | 镜头定格，让玩家感觉到"停了一下" | 无 |

注释里记了一个历史事故：早期用"进空中阶段就开始计时"，导致打完最后一条鱼时
早就超时、结算立刻弹出，"最后那一下击落根本看不清"。rebuild 的 `endT` 口径是对的。

## 四、打击感

### 4.1 命中定格（hitStop）—— 旧项目打击感的第一来源

```js
// game.js:2004
if (this.hitStopT > 0) { this.hitStopT -= dt; dt *= TUNING.hitStopScale; }

// game.js:1191
_hitStop(hp) {
  const k = Math.min(1, Math.max(0, (hp || 0) / 200));
  const sec = 0.04 + (0.12 - 0.04) * k;     // 血越厚停得越久
  this.hitStopT = Math.max(this.hitStopT, sec);   // 取 max，不覆盖
}
```

三个要点：
1. **只压 dt，不暂停渲染**——画面还在画，只是世界走得慢，那才是"顿一下"的手感。
2. **时长按血量**：打碎沙丁鱼几乎看不出来，打中血牛明显一顿。
3. **取 max 不覆盖**：连发枪一秒十几发，覆盖的话后一枪会把前一枪的定格**缩短**，
   结果是"射速越高越没有打击感"，和直觉相反。

**rebuild 完全没有这个机制。** 这是成本最低、收益最高的一项（一个乘数而已）。

### 4.2 击飞反馈的差异

| 环节 | 旧项目 | rebuild |
| --- | --- | --- |
| 冷却 | 逐鱼 `knockT = 0.3s`，防止连发枪把速度叠到 2000+ 飞出大气层 | **无冷却**，`vy = max(0,vy) + boost` 会累加 |
| 增量依据 | `base + min(hp, 16) × 12`（**按剩余血量**） | `12 + n×6 + …`（**按第几枪**） |
| 封顶 | `knockUpMaxHp = 16`（hp 120 的 Boss 不会被一枪顶出大气层） | 无 |
| 飘字 | **「还差 N 枪」**（`ceil(hp/dmg)`） | 直接显示剩余血量 `${a.hp}` |
| 中弹膨胀 | `scale × (1 + hitFlash × 1.6)` —— 鼓一下 | 挤压回弹 `(1.24, 0.8, 1.1)` |
| 火星 | `burstSparks(6, 0.7)` | 12+n×4 颗 |
| 震屏 | `addShake(2.2)`（命中）/ `4.5`（开火）/ `12`（撞鱼） | `camShake.mag += 3.2 + n×1.1` |

**「还差 N 枪」比"剩余血量 3"有用得多**——玩家不需要知道伤害数值，只需要知道还要点几下。

### 4.3 慢动作

| | 旧项目 | rebuild |
| --- | --- | --- |
| 出水瞬间 | `timeScale = 0.28`，持续 **0.22 秒**（全局 dt） | **无** |
| 空中持续 | — | 「子弹时间」升级：0.86/0.74/0.62 倍速（只作用于鱼，不作用于镜头） |

旧项目的慢动作是"离水那一瞬的哇"，rebuild 的子弹时间是"整段变慢"的升级道具。
两者可以共存——出水瞬间慢 0.2 秒不会影响难度，纯粹是表演。

### 4.4 开火反馈

旧项目按武器分级：

| 动作 | 震屏 |
| --- | --- |
| 普通开火（半径 < 50） | 4.5 |
| 重武器开火（半径 ≥ 50） | 9 |
| 榴弹出膛 / 爆炸 | 3.5 / 7 |
| 命中（每发额外） | 2.2 |
| 下潜撞鱼 | 12 |

还有一个细节：`_aimPoint()` 里有**手指偏移补偿** `ny - 0.045`——
"指肚会盖住落点，把判定往上挪一点，玩家看到的才是'我指哪儿打哪儿'"。

## 五、其他值得参考的

### 5.1 天空目标（rebuild 完全没有）

旧项目在空中阶段会持续刷新**海鸟 / 飞机 / UFO**（`config.js:2954`），
每 1.6~4.2 秒一个、最多同时 3 个，按高度分层：

| 目标 | 高度（屏比例） | 血量（5 图） | 身价（5 图） | 速度 |
| --- | --- | --- | --- | --- |
| 海鸟 | 0.14~0.38 | 2~6 | 60~1500 | 46~86 |
| 飞机 | 0.44~0.66 | 8~30 | 260~6200 | 64~104 |
| UFO | 0.70~0.92 | 18~62 | 800~18000 | 30~58 |

两个原则值得记：
- **它们不拦结算**（只数鱼）。历史事故：把飞鸟算进未完成条件，鸟只要在屏幕上就永远不结算，玩家干等 20 多秒。
- **只跟"中过弹"的目标**。没中弹的只是路过，抢镜头只会让画面在结算前乱甩。

### 5.2 抛竿的手感差异

| | 旧项目 | rebuild |
| --- | --- | --- |
| 模型 | 真实物理：初速 130 / 重力 −300 / 滞空 1.16s | 贝塞尔插值（t 0.4~0.86 线性 + sin 拱形） |
| 滞空操控 | `castSteer = 34` **加速度增益** + `castDrag = 1.5` 阻尼 + `castMaxVx = 96` | `vx = clamp(dx × 9, ±11)`，一阶跟随 |
| 手感 | 有惯性的"甩"，松手会飘一下 | 直接吸到指针，指哪落哪 |

rebuild 的一阶跟随更"听话"，旧项目的二阶模型更"重"。这不是谁对谁错，
但如果想要"甩杆"的实感，旧项目的二阶参数可以直接抄。

### 5.3 串鱼的排列

| | 旧项目 | rebuild |
| --- | --- | --- |
| 布局 | **黄金角（2.4 rad）散布 + 索引 hash 抖动**，全挤在钩子下方一个圈里 | 6 条一圈的规则环形，超过 6 条往外扩一圈 |
| 每帧确定性 | 用 `sin(i×12.9898 + k×78.233)` 做伪随机，**同一个 i 永远在同一位置** | 用 `lerp(target, dt×14)` 平滑 ✓ |
| 渲染上限 | 30 条，超出只计数不建模型 | 无上限 |

旧项目那段注释说得很到位：

> 「位置必须**确定性**（用索引做散列，不能用 `Math.random`）：每帧都会被调用，
> 用真随机的话每条鱼每帧都会瞬移，看起来像在抽搐。」

rebuild 用 lerp 规避了同样的问题，达到同样效果但更省事。**这条不用改**。
不过"黄金角散在同一个圈里"比"6 条一圈的规则环"更像一捆活的鱼，可以借鉴。

## 七、一句话结论

旧项目的"沉"来自三件事：**速度快慢有节制**（下潜 0.31 屏/s）、
**每一段运动都带惯性**（刹停滑行 + 起拉 anticipation）、**命中要停一下**（hitStop）。
现在的 rebuild 三件事都反着来：下潜更快、turn 是急刹静止、没有定格。

**先做 P0 的四条**，观感就能拉回来一大半；P1 的 #5/#6 是"衔接"的正解，
但会改动咬钩节奏，建议做完出截图再定。

## 七、落地记录（14 项全做）

上面 P0/P1/P2 一共 14 条，已全部实现。下面是每条的具体做法和实测数据。

### 7.1 P0 · 打击感

| # | 做法 | 实测 |
| --- | --- | --- |
| 1 | 收线相机 `k: 5.5 → 12`，并加 lead：`target += -lureVy / k` | 收线时「镜头 − 钩子」间隔稳定在 **3.07m**（设计值 3.1），改之前会拉到 5.5m |
| 2 | `hitStopT`：命中时 `dt × 0.05`，时长 `0.035 + 0.075 × min(1, hp/8)`，取 max 不覆盖 | hp=5 时 **0.082s**；连打两枪仍是 0.082（既不叠加也不被缩短） |
| 3 | 击飞转速改成 `a.vr += sign(a.vr) × rand(5,12)` | 不再出现「第二枪反向抽筋」 |
| 4 | 飘字从剩余血量改成「还差 N 枪」 | `ceil(hp / dmg)`，霰弹枪 7 颗弹丸时读数仍然准 |

额外加了 **0.22s 的顶飞冷却**（旧项目是 0.3s）：连发枪（uzi 12 发/秒、加特林 20 发/秒）
不做节流会把同一条鱼顶出大气层。

### 7.2 P1 · 运动曲线

**刹停（turn）**：不再静止 0.5 秒，改成「带着下潜速度再滑一段、匀减速到 0」。

```
y = y0 − D(2u − u²)     D = v0 · T / 2     T = 0.5s
```

实测：刹车前 vy = 7.55 m/s → 滑行 **1.88m** 才停（正好等于 v0·T/2）。
另外钳了剩余深度 `min(D, maxDepth + lureY)`，触底时退化回纯停顿。

**起拉（ascent）**：前 0.6 秒走

```
y = y0 + D(3u³ − 2u²)    D = 收线速度 · T / 5
```

起手速度 0、u≈0.44 处**先往下沉 13.2%·D**、末端速度 5D/T 正好接满速。
实测：D = 1.59m 时下沉 **0.206m**。`vy` 按曲线真实斜率同步（`−(D(9u²−4u))/T`），
出 ramp 时不会「突然有速度」。

**下沉构图**：`camOffset` 深处 3.4 → **4.6m**，钩子从屏幕 37% 提到 29%，
下方预视从 62.6% 提到 70.6%（旧项目是 80%）。

**其他**：空中相机改跟「最低的那条」（旧项目同策略）+ lead；
出水瞬间 `slowT = 0.22s`，世界 0.32 倍速。

### 7.4 P2 · 抛竿改二阶物理

```js
// 出手：水平初速 = 落点距离 ÷ 预估滞空，保证还是往指针方向甩
vy = -7;  vx = clamp(dist / fall, ±6.5);
// 滞空：加速度追指针 + 阻尼（二阶），落点可控但有惯性
vx += clamp((want - x) * 7, ±14) * dt;
vx *= (1 - 3.2 * dt);
vy += 16 * dt;   y -= vy * dt;   // 正向为下潜速度
```

落点实测：targetX 2.26 → landX **2.22**；targetX 0 → landX **0.11**。
入水后 0.3 秒接 `descent`，另有 2.8s 保险丝防止卡在 cast。
顺带把「岸边点哪儿、钩子甩哪儿」补上了 —— 原来 `startTrip` 会把落点重置回 0.9。

### 7.7 补漏（同日晚些）

上一版末尾列的三个「还差什么」，补完了；过程中又揪出一个数据污染。

**① 结算页显示天空目标**

```
毛收入            +$904
└ 击落 UFO ×1      +$800
渔获
  小黄鱼 ×5
```

`TripResult` 新增 `skyGain`，`hitSky()` 累加；结算页从 `kills` 里筛 `sky_*` 单独渲染一行，
前面标「└」表示它已经算在毛收入里，不会再加一次。

**顺手修的数据污染（真 bug）**：`App.tsx` 把 `r.kills` 的所有 key 都当鱼种写进存档的 `caught` ——
天空目标一落地，图鉴就会多出 `sky_bird` 这种不存在的鱼，「x/24」会变 x/25。
现在两处都过滤了 `sky_` 前缀，并在 `loadSave()` 里按 SPECIES 清一遍老存档。

**② 云层加高**

从 5 层（最高 70m）加到 **8 层（11 / 19 / 31 / 47 / 70 / 98 / 132 / 175m）**，
越高尺寸越大、透明度越低。飞到 26m 时 19m 和 31m 两层都在画面里。

**③ 抛竿落点**

前两版都不对：先「加速度追指针」会冲过头（中间点误差 1.17m），
换成弹簧阻尼 `a = k·err − c·v` 又够不到远处（左端点差 0.87m）。

正解是**按剩余滞空时间反算速度**：

```js
const remain = (-vy + Math.sqrt(vy * vy + 2 * g * y)) / g;   // vy 向下为正
const desired = clamp((want - x) / remain, ±7.5);
vx += (desired - vx) * min(1, dt * 18);                      // 短平滑，留一点惯性
```

⚠ 第一版把符号写错了（`(vy + √…)/g`），算出来的剩余时间是 0.18 秒而不是 1.05 秒，
钩子被限速卡住、反而飞不到位。这种「公式对但符号反」的错，只有靠落点实测才看得见。

实测落点误差：左 **0.05m**、中 **0.03m**、右 **0.00m**。
